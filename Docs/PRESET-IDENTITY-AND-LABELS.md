# Preset identity and Core Audio channel labels

Status: implemented and built as a signed candidate, 2026-10-24. Automated tests and the live Core Audio clear/copy probe pass. Native driver UID reappearance and restart persistence remain installation acceptance tests; the package is now installed on disk, awaiting the user’s Mac restart. Import/export is deferred.

## Purpose

A user can take the same computer between studios with different interfaces, routing, channel counts and audio settings. Each StudioPatch preset should present a distinct virtual audio device to macOS, allowing Core Audio and audio applications to associate settings with that setup.

## Ownership

| Information | Owner and behavior |
|---|---|
| Physical interface channel names | Read from Core Audio. StudioPatch displays external changes promptly and does not write these names or preserve an original-name history. Existing last-known metadata for disconnected interfaces is not an original-name history. |
| Virtual channels' automatic names | Generated by StudioPatch from the current routing and current physical channel names. These are the driver's default names. Existing fallbacks for unconnected channels and combined names for multiple destinations remain relevant. |
| Virtual channels' manual labels | Owned and persisted by Core Audio, associated with the virtual device's UID, direction and channel number. StudioPatch reads and edits these through Core Audio. |
| Preset configuration and identity | Owned by StudioPatch: routing, channel counts, underlying interfaces, audio settings and a stable identity used for the virtual device UID. Manual labels are excluded. |

StudioPatch must not maintain a separate persistent registry of manual labels in its session, presets or another application store. Reading current names into memory for display, or temporarily holding labels for an explicitly requested copy operation, does not establish another owner.

## Preset identity

- Each preset has a unique, persistent virtual device UID.
- Saving changes to an existing preset, editing its configuration or renaming it preserves its UID.
- Returning to a preset, including after restarting StudioPatch or the computer, reuses its UID.
- Creating a new preset with **Save current as new** gives it a new UID, including when labels are copied.
- UID identity must not depend on the preset's visible name, routing or labels.
- With only the active preset's virtual device exposed, switching to another preset is a device change. Audio applications may stop, select another device or require the user to select the new device. Seamless audio across this change is not promised.

The discussed display-name convention is `StudioPatch (<preset name>)`, for example `StudioPatch (UFXIII+ZEDR16)`. Display naming is separate from persistent identity; application refresh behavior still needs practical verification.

## Live label behavior

- Editing a virtual channel's label in StudioPatch writes it to Core Audio.
- Editing that label in Audio MIDI Setup is reflected promptly in StudioPatch, including the routing matrix, without a manual refresh or application restart.
- A manual label belongs to the virtual channel within that preset's device identity. It stays on that channel when its routing changes.
- Clearing a manual label removes the override. The channel returns to its routing-derived name and continues following subsequent routing/name changes.
- Automatic names must not become manual labels merely because StudioPatch reads or displays them.
- External changes to physical interface names are read and displayed. They can also affect routing-derived virtual names where no manual virtual label overrides them.
- A pure label edit must not reconfigure routing or restart audio.

Manual label changes do **not** mark a preset as modified. They do not add `*` beside the preset name, whether the change originates in StudioPatch or Audio MIDI Setup. Other configuration changes continue to use the existing modified-state behavior.

Saving or loading a preset does not save, restore or overwrite its manual labels. Core Audio retains the latest labels associated with its UID. Users are responsible for label edits; there is no label snapshot or restoration feature in normal preset handling.

## Save current as new

After the user chooses to save the current configuration as a new preset, ask whether its manual channel labels should follow it. Provide a choice to copy the labels or create the preset without them, and allow cancellation before committing the operation.

| Choice | Result |
|---|---|
| Copy labels | Create the new preset with its own UID and apply the source virtual device's current manual labels to the corresponding input/output channels of the new virtual device through Core Audio. |
| Do not copy labels | Create the new preset with its own UID and no manual labels. Its names come from its routing. |
| Cancel | Do not create or activate a new preset. |

Only effective names that differ from the driver’s current automatic names are copied. This simpler rule was explicitly accepted on 2026-10-24: HAL’s public name getter does not expose whether an equal string is an alias. An explicitly entered label equal to the automatic name therefore becomes automatic in the new preset; the source remains unchanged.

Copying is a one-time transfer between Core Audio device identities. It does not put labels into the new preset, link the two devices' future labels or change the source device's labels. Later edits to either device's labels are independent and do not mark either preset as modified.

The source labels must be obtained before switching away from its device. A failed copy must be reported; the UI must not claim that all labels were copied when only some or none were applied. Exact failure recovery and UI wording remain implementation design details.

## Future import/export option — deferred

Import/export enhancements are **not part of this work**. The following is a possible future way to transfer labels alongside a preset without changing their normal ownership:

1. Export could ask whether to include the preset device's current manual labels.
2. If included, the export package could contain an optional label payload alongside the StudioPatch preset configuration.
3. Import could first create/import the StudioPatch preset and then apply the optional labels through Core Audio to its resulting virtual device identity.
4. After application, Core Audio would own those labels. Normal preset files and modified-state comparisons would still exclude them.

The optional payload would preserve manual overrides and automatic channels distinctly. Export/import identity rules, collision handling, behavior for an inactive preset and the file format are future design decisions. No new import/export workflow is to be implemented now.

## Evidence and verification still needed

Read-only investigation on 2026-10-24 found a manual StudioPatch input name stored separately from the driver's published names, under the device UID in macOS audio settings. Reading that channel through Core Audio returned the manually changed name. Core Audio reported the channel-name property writable even though the current driver reports its own channel-name property as read-only.

`Tools/channel-label-probe.mm` verified setting, copying, clearing with an empty CFString, and element-specific notifications in both directions on disposable private aggregate devices. After clearing, names followed subsequent changes to the test device’s defaults. An equal-text manual alias remained sticky when those defaults changed, confirming the need for the accepted copy rule. The macOS settings file was diagnostic evidence; implementation uses public Core Audio APIs, not its private file layout.

An additional private-aggregate destroy/recreate experiment did **not** retain its labels. Explicitly deleting an aggregate is a different lifecycle from removing/adding a native driver endpoint; this result does not establish native driver persistence. No production StudioPatch or physical channel names were changed by the probes. See [verification record](LABEL-VERIFICATION.md).

Before implementation can be considered ready, verify:

- Setting and clearing manual input and output labels through Core Audio, including return to changing automatic names after clearing.
- Receiving channel-specific change notifications and updating the panel promptly without feedback loops or audio reconfiguration.
- Copying only effective names different from defaults; equal-text aliases intentionally become automatic in the destination.
- Label persistence when a device disappears and returns with the same UID, across application/computer restarts, and when channel counts shrink and grow.
- Separation between different preset UIDs and independent labels after **Save current as new**, both with and without copying.
- Exclusion of labels from preset serialization, ordinary save/load behavior and the `*` modified-state comparison.
- The observed behavior of Audio MIDI Setup and supported DAWs during device identity/name changes, including any integration currently assuming the single fixed StudioPatch UID.

## Persistence

Every newly created preset, including the initial default, receives a UID derived from its new UUID. Rename and overwrite retain the destination identity. Loading existing presets uses their stored identities without converting or rewriting the library.

Manual labels are stored only in Core Audio. The old app-owned label field and its migration, backup and retry workflow have been removed. Older app-owned labels are ignored; no automatic transfer is performed.

Copy failure leaves the new preset saved and reports the remaining labels. A transient in-memory queue supports retry or explicit discard, including returning to the destination preset first. Closing the panel loses that pending transfer; no labels are written into presets to persist it.
